# Design

## Context

Lihat `proposal.md` untuk motivasi dan `specs/platform-and-quality/spec.md` untuk kontrak perilaku.

Kondisi saat ini yang membentuk desain:

- `server/src/db.js` membuat instance `better-sqlite3`; seluruh query di `server/src/app.js` memakai API synchronous `prepare()`, `get()`, `all()`, `run()`, dan `lastInsertRowid`.
- Migration memakai file SQL bernomor di `server/migrations/` dan mencatat status di `schema_migrations`.
- `server/src/app.js` menggabungkan routing, validasi, query, mapping respons, dan static serving.
- API yang harus dipertahankan memakai integer ID, `created_at` string UTC `YYYY-MM-DD HH:MM:SS`, deadline `YYYY-MM-DD`, `is_default` boolean, envelope `{ success, data }`/`{ success, message, errors }`, dan pencarian case-insensitive yang meng-escape `%`/`_`.
- Database lokal berisi data yang harus dipertahankan; file `server/data/tasks.db` tidak boleh diubah oleh proses migrasi.
- Target deployment memisahkan frontend Vercel, backend Render, dan database Neon; backend belum memiliki authentication dan memerlukan health check Render yang memeriksa konektivitas database.
- Change `add-public-landing-page` sedang berjalan dan tidak boleh diubah atau diarsipkan.

## Goals / Non-Goals

**Goals:**

- Menyediakan runtime PostgreSQL async yang dapat diuji dan di-deploy tanpa mengubah perilaku API.
- Mempertahankan data, ID, relasi, urutan kategori, dan format respons yang teramati.
- Memisahkan konfigurasi development, testing, deployment, runtime, dan migration.
- Membuat importer yang aman, dapat diaudit, dan tidak mengubah sumber SQLite.
- Menyediakan jalur rollback yang jelas sampai data serta perilaku terverifikasi.
- Menyediakan health check Render yang memeriksa konektivitas database tanpa membocorkan credential atau detail koneksi.
- Menyiapkan schema untuk multi-user tanpa menerapkan authentication atau ownership behavior.

**Non-Goals:**

- Tidak menambahkan authentication, session, user table, ownership filter, atau multi-user isolation.
- Tidak mengubah endpoint, payload, aturan validasi, atau perilaku UI.
- Tidak mengganti integer ID dengan UUID.
- Tidak menambah platform config file seperti `vercel.json` atau `render.yaml`; konfigurasi platform didokumentasikan.
- Tidak melakukan deployment aktual dalam change ini.
- Tidak menghapus SQLite sebelum migrasi dan verifikasi selesai.

## Decisions

### 1. Drizzle ORM dengan driver `pg`

- Runtime memakai `drizzle-orm/node-postgres` dan `pg.Pool`.
- `DATABASE_URL` menunjuk koneksi Neon pooled untuk runtime Render; `DATABASE_URL_UNPOOLED` menunjuk koneksi langsung untuk migration dan importer.
- Pool runtime dikonfigurasi kecil dan menutup koneksi saat `SIGINT`/`SIGTERM`, sehingga tidak menambah tekanan berlebihan di atas Neon pooling.
- Alternatif ditolak: Neon HTTP driver tidak diperlukan untuk backend Express long-running dan menyulitkan transaksi; `postgres.js` menambah driver baru tanpa manfaat dibanding `pg` yang sudah menjadi target.

### 2. Schema PostgreSQL yang mempertahankan kontrak

- `categories`: integer identity ID, nullable `user_id text`, `name`, `is_default boolean`, `sort_order`, `created_at timestamptz`.
- `tasks`: integer identity ID, nullable `user_id text`, `title`, `description`, `status`, `priority`, `deadline date`, nullable `category_id`, `created_at timestamptz`.
- Gunakan `generated by default as identity` agar ID lama dapat diimpor eksplisit, lalu reset sequence setelah impor.
- Gunakan `text` + `CHECK` untuk status/priority, bukan PostgreSQL enum, agar nilai tetap dapat dikelola oleh validasi aplikasi dan perubahan nilai tidak memerlukan operasi tipe yang rumit.
- Gunakan `deadline date` dengan mode string Drizzle agar API tetap menerima/mengembalikan `YYYY-MM-DD`.
- Gunakan `created_at timestamptz`; mapper API mengubahnya kembali ke format legacy UTC `YYYY-MM-DD HH:MM:SS` agar kontrak tidak berubah.
- Pertahankan `category_id ... ON DELETE SET NULL` dan index yang setara.
- Tambahkan index `user_id` untuk kesiapan masa depan, tanpa memakai kolom tersebut di query.

### 3. Keunikan nama kategori case-insensitive

- Unique index global lama diganti dengan index yang memakai ekspresi `lower(name)`.
- Untuk menjaga perilaku single-user saat `user_id` masih `NULL`, gunakan SQL migration eksplisit:
  `CREATE UNIQUE INDEX idx_categories_user_name_nocase ON categories (user_id, lower(name)) NULLS NOT DISTINCT;`
- Drizzle schema tetap mendokumentasikan kolom dan index; SQL eksplisit dipakai karena kebutuhan `lower(name)` dan `NULLS NOT DISTINCT` lebih tepat dinyatakan langsung di migration.
- Jika target PostgreSQL tidak mendukung `NULLS NOT DISTINCT`, fallback-nya adalah dua partial unique index: satu untuk `user_id IS NULL`, satu untuk `user_id IS NOT NULL`.
- Pengecekan duplikat di aplikasi tetap dilakukan, tetapi unique violation PostgreSQL `23505` juga dipetakan ke HTTP `409` untuk menutup race condition.
- Alternatif `citext` ditolak karena menambah extension dan perilaku case-folding yang tidak perlu; `lower(name)` cukup untuk perilaku saat ini.

### 4. Lapisan akses database dan refactor async

- `server/src/schema.js` mendefinisikan tabel dan relasi Drizzle.
- `server/src/db.js` membuat pool dan instance Drizzle, serta menyediakan fungsi close.
- Query dipindahkan ke `server/src/repositories/{tasks,categories,stats}.js`; `app.js` tetap menjadi tempat route, validasi input, mapping respons, dan error handling.
- Semua handler database menjadi async dan memakai `await`. Express 5 meneruskan rejection async ke error middleware.
- `lastInsertRowid` diganti dengan `.returning()`. Update partial tetap hanya menyentuh field yang dikirim.
- Pencarian memakai `ILIKE ... ESCAPE '\'` agar tetap case-insensitive dan literal `%`/`_` tetap di-escape seperti SQLite.
- Sorting deadline memakai ekspresi boolean `deadline IS NULL`, lalu `deadline`, `created_at DESC`, dan `id DESC`.
- Statistik menggunakan agregasi PostgreSQL dan hasil count dinormalisasi menjadi number.
- Error PostgreSQL yang dapat diprediksi dipetakan ke error aplikasi: unique violation ke `409`, foreign key/constraint ke `400`, error lain ke `500` melalui middleware yang sudah ada.
- Alternatif mempertahankan query mentah di `app.js` ditolak karena query filter dinamis menjadi sulit diuji dan memperbesar risiko regresi.

### 5. Migration, seed, dan startup

- Drizzle Kit menghasilkan baseline schema di `server/drizzle/`.
- Kategori bawaan dimasukkan melalui migration SQL custom yang berjalan sekali, dengan insert yang aman terhadap konflik.
- `server/src/migrate.js` menyediakan migrator programatik untuk test dan CLI.
- `server/src/migrate-cli.js` memakai `DATABASE_URL_UNPOOLED` dan menutup koneksi setelah selesai.
- Server tidak menjalankan migration otomatis saat startup. Migration dijalankan eksplisit sebelum server lokal atau melalui pre-deploy command Render.
- `drizzle-kit` tetap dev dependency untuk generate; migrasi runtime memakai `drizzle-orm` agar tidak bergantung pada tool dev di production.
- Alternatif auto-migrate saat startup ditolak karena dapat menimbulkan race saat scaling, sulit di-rollback, dan memakai koneksi runtime yang salah.

### 6. Importer SQLite

- Importer berada di `server/scripts/import-sqlite.js` dan memakai `better-sqlite3` hanya untuk membaca sumber dengan opsi read-only.
- Sumber default `server/data/tasks.db`; path dapat dioverride melalui argumen.
- Importer memakai `DATABASE_URL_UNPOOLED`, satu koneksi/transaksi, dan menolak target non-kosong kecuali `--replace` diberikan.
- Mode `--replace` melakukan truncate target di dalam transaksi sebelum insert, sehingga menjalankan ulang tidak menggandakan data.
- Data kategori diimpor lebih dahulu, lalu tugas, dengan ID eksplisit dan timestamp yang dikonversi sebagai UTC.
- Setelah insert, sequence `categories.id` dan `tasks.id` di-reset memakai `setval`.
- Mode `--dry-run` membandingkan jumlah, ID, relasi, status/priority, deadline, dan timestamp tanpa menulis.
- Verifikasi pasca-impor mencakup count per tabel, count per status/priority, orphan check, dan sampel data.
- Alternatif upsert per baris ditolak karena tidak memberi jaminan idempotensi sekuat replace transaksional dan lebih sulit diaudit.

### 7. Pemisahan environment dan deployment readiness

- Development: `server/.env` dengan koneksi development.
- Testing: `server/.env.test` dengan Neon branch/database test khusus. Integration test membaca `TEST_DATABASE_URL` dan `TEST_DATABASE_URL_UNPOOLED`.
- Deployment: environment Render memakai `DATABASE_URL` pooled dan `DATABASE_URL_UNPOOLED` direct.
- Test setup menolak berjalan jika `NODE_ENV=production` atau jika URL test sama dengan URL production yang tersedia.
- CORS memakai allowlist `CORS_ORIGIN` berisi origin frontend yang dipisahkan koma; tidak memakai wildcard untuk deployment.
- Frontend memakai `VITE_API_URL` opsional; saat kosong, request tetap relatif dan Vite proxy dipakai untuk development.
- Dokumentasi deployment menjelaskan perintah build/start, migration pre-deploy, environment, SPA fallback Vercel, health check Render, dan batas backend privat.
- Alternatif meng-hardcode URL Render di frontend ditolak karena mengikat build ke satu environment.

### 8. Health check deployment

- `GET /api/health` ditempatkan pada `server/src/app.js` dan memakai koneksi database runtime yang sama dengan API; endpoint tidak memakai `DATABASE_URL_UNPOOLED` atau menjalankan migration.
- Pemeriksaan memakai query read-only ringan `SELECT 1` dengan batas waktu singkat. Endpoint tidak menulis data dan tidak bergantung pada isi tabel.
- Database yang merespons menghasilkan HTTP `200` dengan body `{ "status": "ok" }`. Kegagalan koneksi, query error, atau timeout menghasilkan HTTP `503` dengan body `{ "status": "unhealthy" }`.
- Body respons hanya memuat status. Endpoint tidak mengembalikan pesan error database, credential, host, nama database, URL koneksi, stack trace, atau detail driver.
- Error server-side dicatat secara generik tanpa menyalin `DATABASE_URL` atau detail koneksi ke log.
- Respons memakai `Cache-Control: no-store` agar hasil health check tidak di-cache oleh Render atau proxy.
- Pemeriksaan memakai dependency database yang sudah di-inject ke `createApp(db)` agar test dapat memicu jalur sukses dan gagal tanpa mengubah koneksi global.
- Alternatif health check yang hanya mengembalikan `200` tanpa query ditolak karena tidak membuktikan backend dan database dapat berkomunikasi.

### 9. Strategi testing

- Unit test validasi tetap berjalan tanpa database.
- Integration test API, migration, persistence, dan importer memakai Neon test branch.
- Test files dijalankan serial; state di-reset dengan `TRUNCATE tasks, categories RESTART IDENTITY CASCADE` dan seed kategori sebelum setiap test.
- Test persistence membuat data, menutup pool, membuat pool/app baru, lalu memverifikasi data masih ada.
- Test importer membuat fixture SQLite sementara, menjalankan importer ke database test, lalu memverifikasi ID, relasi, timestamp, sequence, dan source file tidak berubah.
- Test kontrak memverifikasi integer ID, boolean `is_default`, format `created_at`, deadline date-only, envelope error, pencarian case-insensitive, wildcard escaping, sorting, dan statistik.
- Test health check memverifikasi `200` saat database test tersedia dan `503` saat dependency database gagal, termasuk body yang tidak memuat credential, URL, nama database, pesan error, atau stack trace.
- Alternatif mock repository ditolak untuk integration test karena tidak menguji SQL, constraint, FK, dan transaksi PostgreSQL yang justru menjadi risiko utama migrasi; health check tetap memakai integration test untuk jalur sukses dan stub dependency untuk jalur gagal.

## Risks / Trade-offs

- **Refactor sync ke async melewatkan `await` atau error handling** → Review semua repository, gunakan Express 5 async rejection, dan jalankan seluruh integration test.
- **Format `created_at`, boolean, count, atau deadline berubah** → Mapping respons eksplisit dan assertion kontrak di integration test.
- **Pencarian PostgreSQL case-sensitive atau wildcard berubah** → Gunakan `ILIKE ... ESCAPE '\'` dan pertahankan test pencarian yang ada.
- **Keunikan kategori berbeda karena collation/Unicode** → Gunakan `lower(name)` untuk constraint dan `Intl.Collator('id')` tetap dipakai untuk urutan tampilan; test duplikasi case-insensitive.
- **Migration berjalan lewat PgBouncer** → Migration/importer selalu memakai `DATABASE_URL_UNPOOLED`; runtime memakai `DATABASE_URL`.
- **Double pooling dengan Neon pooler** → Gunakan `pg.Pool` kecil, tutup koneksi saat shutdown, dan dokumentasikan konfigurasi.
- **Data hilang atau ID/sequence rusak** → Backup SQLite, transaksi importer, dry-run, verifikasi count/relasi, dan reset sequence.
- **Rollback setelah cutover kehilangan tulisan baru** → Lakukan maintenance window, hentikan backend sebelum export final, dan pertahankan SQLite sampai rollback window selesai.
- **Test mengubah database production** → Environment test terpisah, branch Neon khusus, guard URL, serial execution, dan truncate hanya di database test.
- **Backend tanpa auth terekspos publik** → Dokumentasikan batas deployment dan perlakukan Render sebagai privat/internal sampai authentication tersedia.
- **Health check membocorkan credential atau detail database** → Respons hanya memuat status generik, jangan mengembalikan pesan error/stack, dan sanitasi logging server-side.
- **Health check membebani database atau gagal saat cold start** → Gunakan `SELECT 1`, batas waktu singkat, dan `Cache-Control: no-store`; kegagalan dilaporkan sebagai `503` tanpa detail.
- **Perubahan bersamaan dengan `add-public-landing-page` pada `platform-and-quality`** → Jangan mengubah change tersebut; review konflik spec saat salah satu change diarsipkan, dan jangan mengklaim backend publik aman.
- **Migration deployment terlewat** → Dokumentasikan pre-deploy command dan gagalkan startup dengan pesan jelas jika schema/database tidak siap.

## Migration Plan

1. Buat schema PostgreSQL dan Drizzle migration; verifikasi pada database test baru.
2. Tambahkan seed kategori bawaan dan test migration.
3. Refactor server ke async Drizzle/repository; jalankan integration test terhadap database test.
4. Tambahkan importer dan test importer dengan fixture SQLite.
5. Siapkan environment development/test/deployment, CORS, base URL frontend, dan `GET /api/health`; perbarui dokumentasi.
6. Backup `server/data/tasks.db`, buat snapshot/branch Neon, hentikan backend, dan jalankan importer dry-run.
7. Jalankan importer `--replace` dalam maintenance window, reset sequence, dan verifikasi count/relasi/timestamp.
8. Jalankan API smoke test, health check database tersedia, dan regression test pada data hasil migrasi.
9. Deploy backend dengan migration pre-deploy dan konfigurasi Neon/Render privat; verifikasi CORS, `/api/health` mengembalikan `200`, serta frontend base URL.
10. Setelah rollback window disetujui, hapus runtime SQLite dan `better-sqlite3`; pertahankan backup data sesuai kebijakan operasional.
11. Rollback sebelum verifikasi: hentikan backend, batalkan transaksi impor atau pulihkan branch Neon, lalu gunakan SQLite yang tidak berubah.
12. Rollback setelah cutover: hentikan backend, kembalikan deployment/env ke versi SQLite, pulihkan backup SQLite, dan mulai ulang. Tulisan yang dibuat setelah cutover hanya dapat dipertahankan jika ada prosedur sinkronisasi terpisah; maintenance window meminimalkan risiko ini.

## Open Questions

- URL production Vercel/Render, origin CORS final, dan kredensial Neon belum diketahui dan akan diisi sebagai environment deployment.
- Apakah importer dipertahankan sebagai tool operasional setelah rollback window ditutup; keputusan ini tidak mengubah spec, pendekatan, atau task breakdown.
